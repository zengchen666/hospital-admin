### 1.4 公共字段约定（所有业务表强制适用）

除纯日志表、快照表（`sys_operation_log`、`sys_login_log`、`sys_sms_record`、`sys_report_data`）外，**每张表必须包含以下公共字段**，后文各模块的字段表不再重复列出：

| 字段        | 类型     | 必填 | 说明                              |
| :---------- | :------- | :--: | :-------------------------------- |
| id          | bigint   |  是  | 主键，雪花算法（非自增，避免分表冲突） |
| create_by   | bigint   |  否  | 创建人 ID                         |
| create_time | datetime |  是  | 创建时间，默认 `CURRENT_TIMESTAMP` |
| update_by   | bigint   |  否  | 最后修改人 ID                     |
| update_time | datetime |  是  | 最后修改时间，`ON UPDATE` 自动更新 |
| deleted     | tinyint  |  是  | 逻辑删除：0 正常 / 1 已删除，默认 0 |
| version     | int      |  是  | 乐观锁版本号，默认 0              |

> **落地约束**
> 1. 禁止物理删除。所有 DELETE 接口实际执行 `UPDATE ... SET deleted = 1`，由 MyBatis-Plus `@TableLogic` 拦截，查询自动追加 `deleted = 0`。
> 2. 乐观锁由 `@Version` 注解生效，更新语句自动追加 `AND version = ?`；影响行数为 0 时抛「数据已被他人修改，请刷新」。
> 3. `create_by` / `update_by` 由 MyBatis-Plus 自动填充，禁止前端传值（防伪造）。
> 4. 后续字段表中出现的 `create_time` 等，仅在该表有**特殊语义**时才单独列出（如「开方时间」「收费时间」）。

### 1.5 命名与数据类型约定

| 项         | 约定                                                                 |
| :--------- | :------------------------------------------------------------------- |
| 表名       | `模块前缀_业务名`，全小写下划线，**不用复数**（`biz_patient` 而非 `biz_patients`） |
| 模块前缀   | `sys_` 系统与基础数据；`biz_` 业务数据                               |
| 字段名     | 全小写下划线，禁止拼音、禁止保留字（`desc`、`order`、`key`）         |
| 主键       | 一律 `id bigint`，雪花算法；**不使用自增**，为后续分表留余量         |
| 布尔       | `tinyint`，0 否 / 1 是；禁止 `bit`（JDBC 驱动映射易踩坑）            |
| 金额       | `decimal(12,2)`；**禁止 float / double**。本文档早期表格中出现的 `decimal(10,2)` 一律按 12,2 执行 |
| 时间       | `datetime`，统一 `Asia/Shanghai`；日期用 `date`                      |
| 枚举       | `tinyint` + 数据字典，禁止直接存中文                                 |
| 长文本     | `text`；单字段超过 64KB 改存 MinIO，库中只存文件 ID                  |
| 字符串长度 | 按实际业务定长，禁止一律 `varchar(255)`                              |
| 索引       | 外键字段必建索引；高频查询组合建联合索引；禁止在 `deleted` 单列建索引 |

### 1.6 鉴权与请求头

| Header          | 必填 | 说明                                                     |
| :-------------- | :--: | :------------------------------------------------------- |
| `Authorization` |  是  | `Bearer {accessToken}`，除登录接口外全部需要             |
| `X-Request-Id`  |  否  | 幂等键 / 链路追踪 ID，写操作建议携带                     |
| `Content-Type`  |  是  | `application/json;charset=UTF-8`                         |

**Token 机制**

- `accessToken` 有效期 2 小时，`refreshToken` 有效期 7 天，登录响应同时返回两者。
- 刷新接口：`POST /api/system/auth/refresh`，请求体 `{ "refreshToken": "..." }`。
- **载荷声明**：除标准 `sub/iat/exp/iss/typ` 外，另带三个自定义声明：
  `sid`（会话 ID，一次登录一个）、`jti`（令牌唯一 ID）、`ver`（用户令牌版本号）。
- **刷新轮换**：每次刷新都作废旧 `refreshToken` 并换发新的；旧票据再次使用返回 `40101`
  （防重放——票据被窃取时只能用一次，且真正持有者下次刷新会失败，可及时发现异常）。
- **登出**：销毁 `sid` 对应的会话，该设备此后无法再刷新；`accessToken` 不拉黑，
  最多 2 小时后自然过期（无状态 JWT 的固有特性，避免每请求多一次黑名单查询）。
- **改密 / 禁用 / 强制下线**：`sys_user.token_version` 递增，该用户所有已签发的
  `accessToken` 与 `refreshToken` **立即失效**，下次请求返回 `40101`。
- **多设备**：每次登录生成独立 `sid`，各设备会话互不影响；
  改密、禁用这类操作对所有设备同时生效。
- **科室/角色不从前端传**：服务端从 token 解析 `userId`、`deptId`、`roleCodes`，前端传的 `deptId` 一律忽略，防止越权伪造。

### 1.7 并发控制与幂等

| 场景             | 方案                                                                                     |
| :--------------- | :--------------------------------------------------------------------------------------- |
| 号源扣减         | `UPDATE biz_schedule SET remain_num = remain_num - 1 WHERE id = ? AND remain_num > 0`，影响行数为 0 即返回 40901 |
| 挂号 / 收费提交  | 前端带 `X-Request-Id`，服务端 Redis `SETNX req:{id}`，TTL 5 分钟；重复请求返回 40903      |
| 处方 / 医嘱状态  | 严格状态机流转，禁止直接 `UPDATE status`；见各模块状态说明                                |
| 同患者并发开单   | Redisson 分布式锁，key = `lock:patient:{patientId}`，等待 3s、持有 10s                    |
| 库存扣减         | 条件更新 + 库存流水表 `biz_stock_record` 双向记账，两者必须在同一本地事务内               |
| 报表重算         | 定时任务加 Redis 任务锁，避免多实例重复跑                                                |

### 1.8 敏感数据处理

| 项         | 规则                                                                      |
| :--------- | :------------------------------------------------------------------------ |
| 加密字段   | `biz_patient.id_card`、`biz_patient.phone`、`sys_user.phone` 使用 AES-256-GCM 加密入库 |
| 检索字段   | 加密列无法模糊查询，另建 `id_card_hash`（SHA-256）用于精确匹配，建唯一索引 |
| 展示脱敏   | 身份证 `4403**********01`；手机号 `138****0000`；姓名 `张*`                |
| 解密接口   | 单独接口 `GET /api/patient/{id}/plain`，需 `audit:decrypt` 权限并写操作日志 |
| 导出       | 导出接口一律脱敏；如需明文导出须走审批，文件打水印                          |
| 日志脱敏   | `sys_operation_log.params` 落库前过滤 password、idCard、phone 等字段       |

> ⚠️ **`query_sql` 是整份文档里风险最高的一列**
>
> 允许前端直接存 SQL 并执行，等于把数据库交给了任何人。三条硬约束必须同时生效，缺一条就不要做这个功能：
>
> 1. **不在库里存可执行 SQL**：改为存「数据集 ID + 维度/指标/过滤条件」的 JSON 配置，SQL 由后端按模板拼装（如 `query_sql` 改名 `config_json`，仅允许引用预定义数据集）。
> 2. **若确需存 SQL**：必须语法白名单校验（只允许 `SELECT`，禁止 `;`、`--`、`/*`、`INTO OUTFILE`、`information_schema`），且禁止拼接用户输入。
> 3. **执行隔离**：用只读账号（仅 `SELECT` 权限）执行，并设置 `statement timeout = 10s`、`max rows = 10000`。
>
> 一期建议**直接砍掉自定义 SQL**，只做 5 张固定报表 + 导出的下拉筛选。自定义报表放三期。

> **相对设计的四处调整（实施期确定）**
>
> 1. **公告拆成「新建 + 发布」两个动作**：设计里只有一个 `POST /api/notice`（发布公告）。
>    合在一起意味着写一半点错了就全院都收到，故改为新建一律落草稿，确认后再显式发布。
> 2. **已发布的公告不可改、不可删**：通知发出去后悄悄改内容，看过旧版的人和新版对不上。
>    要改只能删草稿重发 —— 因此 `PUT/DELETE /api/notice/{id}` 只对草稿生效，对已发布返回 `40902`。
> 3. **新增 `/api/notice/visible`**：设计里没有「我可见的公告」这一路，公告分页是管理视角（含草稿）。
>    首页/消息中心要的是「已发布 + 院内或本科室」，两个视角混用会把草稿漏给所有人。
> 4. **站内消息不提供删除接口**：`sys_message` 是流水型表，没有逻辑删除字段。
>    消息是「系统告诉过你什么」的证据，用户只能标记已读，不能让它消失。
>
> **预警列表不落库**：`/api/warning/list` 每次实时聚合药房（库存 / 效期）、检验（危急值）、
> 公卫（传染病超期 / 疫苗逾期）五路数据。落库就变成快照 —— 库存补上了预警还在，
> 用的人发现不准就不会再点开，而预警的全部价值就在于「此刻确实有问题」。
> 单个数据源查询失败只跳过该源并记 error 日志，不影响其它源。

## 附录 B：核心表关系（文字版 ER）

```
【权限域】
sys_dept ──< sys_dept (parent_id 自关联，科室树)
sys_dept ──< sys_user (dept_id)
sys_user ──< sys_user_role >── sys_role

biz_patient ──< biz_medical_record
biz_patient ──< biz_follow_up

【挂号→门诊】
sys_user(doctor) ──< biz_schedule >── sys_dept
biz_schedule ──< biz_registration >── biz_patient
biz_registration ─1:1─ biz_medical_record   (一期以 registration.id 充当 visit_id)
biz_registration ──< biz_prescription
biz_prescription ──< biz_prescription_item >── biz_drug
biz_registration ──< biz_exam_apply

【住院】
biz_ward ──< biz_bed
biz_patient ──< biz_admission >── biz_bed / sys_user(doctor,nurse)
biz_admission ──< biz_medical_order
biz_admission ──< biz_nursing_record

biz_warehouse ──< biz_stock >── biz_drug

biz_prescription ──< biz_dispense ──< biz_dispense_item >── biz_stock(按批号扣减)

【检查检验】
biz_exam_apply ──< biz_exam_item        (一申请多项目)

【收费】
biz_treat_item ──< biz_charge_item      (成交价快照，不随字典改价变动)
```

> `──<` 表示一对多，`>──` 表示多对一，`─1:1─` 表示一对一。
> 本设计**不使用数据库外键约束**（利于分表与数据迁移），外键关系由应用层保证。
> 索引策略：**按查询路径建索引，不盲目给每个 `*_id` 建索引** —— 患者/科室/医生/库房/处方等高频过滤列必建；`operator_id`、`auditor_id` 这类审计列不建（写放大，且从不作为过滤条件）。
